# Conditional Capability Completion

This cold-path module owns professional judgment about whether an exact
delivery-state claim is supported across the necessary capability dimensions.
It contributes `capability_claim` to the one current
`cotend.execution-closure.v1` result owned by
`semantic-contract-templates.md`. It does not own another packet, capability
tree, project truth file, standing dashboard, or six-axis report.

Load it with `acceptance-test-harness.md` only when a trigger below fires.

## Triggers

- A user/AI statement would make a decision-relevant claim of completion,
  availability, integration, readiness, activity, end-to-end delivery,
  implementation/build, working/runnable behavior, landing, or equivalent
  delivery state.
- The user asks whether an exact capability or outcome has reached such a
  state.
- A protected semantic write would change an existing capability/navigation
  `status`, `current`, `active`, or `next` assertion.
- An important current-MVP L2/main-chain node is being closed or navigation may
  advance.
- Route Rebase or a changed semantic/design/implementation/verification premise
  makes an earlier result unsafe and requires freshness re-evaluation.

These are semantic categories, not a keyword list. Quoted history, changelog
text, an ordinary progress note, a semantic draft, scoped alignment, a routine
test or a small L3/L4 implementation does not trigger merely because it uses a
delivery word. Apply the guard from evidence; do not ask the user to approve
AI-owned delivery dimensions.

## Contribution Boundary

Reuse the current `execution_closure` result for the exact scope/epoch and
contribute only:

- the exact claim wording and stable capability/parent IDs when they exist;
- which of the six canonical dimensions are required for that wording;
- dimension facts that point to the shared basis/acceptance evidence;
- exact-scope and conservative parent/child results;
- safe wording and material gaps.

The schema, six field names, evidence/status enums, freshness states and
deterministic result order are defined once in
`semantic-contract-templates.md`. Do not restate or translate them here.
Acceptance owns observations; Semantic Implementation Closure owns material
boundaries and route advance.

## Exact Scope And Stable Identity

Start from what the sentence would cause another actor to believe. A narrow
claim such as “candidate enumeration implementation passed its unit tests” has
different required facts from “relationship analysis is complete and
available end-to-end.” Never let evidence for the narrow slice support the
broader promise.

When an existing capability tree or stable IDs exist, reuse them. If required
children have heterogeneous results, include separate claim items inside the
same execution result for those IDs. Do not collapse them into a free-text
parent or create a parallel tree. A parent is supported only when its own
required dimensions and every required child are supported; a missing,
partial, blocked or unknown child keeps the parent non-supported.

Always include the exact-scope root claim. The shared
`capability_claim.overall_result` copies that root's canonically derived result
after required-child aggregation; it is never an independently chosen summary.
A missing root or mismatch remains unknown and cannot drive STATUS, handoff,
Done or navigation.

A small project without stable IDs may use one precise natural-language exact
scope. At least one dimension must be required. A non-required dimension needs
a concrete reason; missing evidence is not non-applicability. If a project has
an `operations` axis, map it to the canonical `operational` dimension without
emitting both or creating a seventh axis.

## Six-Dimension Judgment

Expand only dimensions necessary to the decision-relevant exact claim:

- **semantic** — the applicable protected outcome and boundaries are complete
  for scope, user-confirmed where required, current, aligned and uniquely bound
  at this trigger;
- **implementation** — active code/entrypoints implement the stated
  responsibility, not just an isolated object or dormant path;
- **data** — required real/representative data, identity, migration, durability
  and edge states support what the claim promises;
- **integration** — actual upstream input reaches the implementation and its
  output satisfies the downstream interface/behavior contract;
- **verification** — outcome-corresponding evidence exercises the exact active
  path and required cases; proxy/inspection limits remain visible;
- **operational** — configuration, runtime availability, degraded/blocked
  behavior, observability/recovery and other readiness facts required by the
  wording are supported.

Small, reversible, non-decision-relevant L3/L4 work does not pay this cost. For
a narrow triggered claim, dimensions genuinely outside its wording remain
non-required with reasons rather than acquiring ceremonial checks.

## Freshness And Evidence Reuse

Use the shared `execution_closure.basis`. Bind the exact claim to every
required semantic contract, the minimum sufficient implementation identity,
any triggered Project Intelligence/design reference, the active Route Rebase
result when applicable, and every verification identity relied upon.

- A changed/mismatched protected contract or materially changed implementation
  or verification identity makes the dependent basis stale.
- Missing, ambiguous, unverifiable or `legacy_unbound` protected evidence, an
  unknown implementation identity, or an empty required verification pointer
  makes it unknown.
- Formatting-only semantic changes preserving the verified canonical digest do
  not invalidate freshness.
- Scope identities are minimal: do not hash the whole repository when a
  component/file-set/runtime snapshot is sufficient.
- A changed basis invalidates only dependent claims/paths. An independently
  evidenced route may continue.

Old evidence can reduce rework but does not preserve its conclusion. Rerun or
explicitly revalidate it against the current protected outcome, design, active
code/data/interface/entrypoint and real runtime conditions.

## Result And Safe Wording

Apply the canonical derivation in `semantic-contract-templates.md` exactly.
Blocked facts outrank support; supported requires current freshness and every
required dimension/required child; stale known support becomes partial;
wholly missing/deferred/not-run evidence stays unknown. Inspection never
becomes executed behavior, and a rule assertion does not prove runtime
behavior.

When a claim is not supported, replace the original delivery wording with a
precise safe statement that names what current evidence proves and the gaps.
Do not preserve a broad “complete/working/ready” assertion in a caveat while it
still controls STATUS, Plan Tree, handoff, Done, acceptance or navigation.

A user-confirmed degraded contract may support exactly that degraded outcome
when direct evidence proves it. AI cannot invent a smaller protected promise to
obtain support. Fixture-only/empty-data evidence cannot support a broad
real-data or end-to-end claim.

## Legacy Compatibility

Existing `capability_completion_claim` records remain lazy historical input.
Normal update/init/continue does not scan, migrate, merge or rewrite them. At
the next real claim/closure/freshness trigger, preserve useful stable IDs and
evidence references, re-evaluate the exact scope and current basis, and write
only one successor `execution_closure`. A stale/unknown old supported label
cannot control current state.

Full and Adaptive use identical scope, applicability, freshness, dimension
facts, parent/child aggregation, safe wording and result. Runtime profile may
change scaffolding only; it cannot grandfather evidence or widen a claim.
