# Project Intelligence

This module is the sole behavior owner for the triggered
`cotend.project-intelligence.v1` cold path. It establishes a project from a
fuzzy idea, reconstructs enough understanding for route responsibility, or
refreshes an affected project/design model after change or contrary evidence.
It also owns decision-relevant understanding entities and the cross-node
`thesis | concept | invariant` relations that let several Plan Tree nodes refer
to one meaning without copying it.
Collaboration, Plan Tree, Semantic Alignment, Project Init, Session Handoff,
DMU, Closure, Acceptance, Solution Adequacy, and Diagnose may detect, invoke,
link, or consume the same result. They must not copy its trigger, scope,
synthesis, design, freshness, question, stop, or permission algorithm.

Project Intelligence is read-only with respect to protected product meaning.
It may maintain AI-owned professional design in an existing fact owner, but it
creates no semantic baseline, L2.5 layer, second Plan Tree, project-truth file,
design or understanding ledger, hook, background process, graph database, or
mandatory document set. Direct
`$cotend-semantic-alignment` remains the only owner that confirms and writes
protected current-MVP L0-L2 meaning. Plan Tree remains the only route tree, and
current objective evidence remains the authority for implementation reality.

Owner precedence is explicit: Project Intelligence owns understanding/design,
Plan Tree owns navigation, and Semantic Alignment owns protected confirmation.
Non-owner README/understanding mirrors are evidence/presentation; disagreement
is a bounded `stale_mirror` maintenance finding. Use `authority: conflict` only
for unresolved incompatible decisions from peer owners.

## Select One Purpose, One Scope, And Only The Needed Views

Choose one purpose from the actual trigger. Do not serially run three complete
workflows or fill unrelated empty sections.

| Purpose | Use when | Required result |
|---|---|---|
| `establish_from_idea` | A fuzzy idea, product concept, substantial feature sketch, or designated intake artifact begins work or materially interrupts the current direction. | Form an AI-first candidate thesis and minimum project model, then ask only high-leverage user-only questions and hand any protected delta directly to Semantic Alignment. |
| `reconstruct_for_responsibility` | The root Primary first assumes end-to-end responsibility, an explicitly invoked same-Primary session takes over, a confirmed new Primary/DMU takeover occurs, or L0/L1 is materially rebased. | Recover the current decision's structurally complete four-plane model and its active-leaf-to-main-chain connection. |
| `refresh_affected_model` | Work enters a new/changed domain, crosses material dependencies, encounters drift/rework/route rupture, lacks necessary design before an important L2 boundary, changes foundational architecture, goal-derived pressure exposes a plausible current lock-in, or reality falsifies an assumption. | Refresh only the affected planes, design views, evidence obligations, and declared dependencies. |

Select the widest minimum scope implied by all current reasons:

| Scope | Canonical reasons | Minimum boundary |
|---|---|---|
| `full_current_project` | `fuzzy_idea_establishment`, `first_project_entry`, `same_primary_new_session`, `confirmed_primary_takeover`, `l0_l1_full_rebase` | Complete current value/long-term direction, current-MVP main chain and L1 map, important L2 relationships, current reality, design basis, candidates/unknowns/history, and recent relevant changes. |
| `affected_l1_domain` | `new_l1_domain`, `l2_scope_change`, `cross_domain_architecture_or_cumulative_main_chain`, `foundational_design_choice`, `pre_important_l2_design_gap`, `goal_evolution_lock_in_probe` | Affected L1(s), important contained L2s, direct upstream/downstream/cross-domain dependencies, relevant value/design/reality/history views, and the active L2 in full. |
| `active_path_delta` | `drift_rework_route_break_or_stale_assumption`, `assumption_falsified` | Active path, parent chain, declared dependents, and relevant changes since the last reliable boundary; widen as soon as the anomaly cannot be bounded. |

The five selectable views are `project_thesis`, `value_and_product`,
`design_and_architecture`, `current_reality`, and
`candidates_unknowns_history`. `full_current_project` requires all five.
Local scopes reuse current unaffected references and refresh only views needed
by the trigger. Purpose does not determine read volume; scope and selected
views do.

Legacy `full_current_mvp` records are compatibility input only. Do not scan or
rewrite them during ordinary update/init/continue. At the next real Project
Intelligence trigger, use their still-current evidence as basis/history and
produce `full_current_project` when a full scope is required. A legacy record
without four-plane synthesis and long-term value cannot establish new
readiness by itself.

## Trigger And Zero-Load Boundary

The root Primary lifecycle owns first-entry responsibility. A bounded worker,
reviewer, or subagent seeing the repository for the first time consumes the
root's compact packet and canonical pointers; that view alone is not a trigger.

Do **not** load this owner for ordinary `continue`/`继续`, the next L3/L4 leaf on
the same confirmed route, a known small bug or parameter correction, local
implementation/test/refactor detail, repeated verification, formatting/docs,
a narrow advisor slice, or an interesting future scenario with no derivation
from the project goal. Do not reload it when the affected result and every
declared basis remain current.

Generating, refreshing, or formally reviewing a material understanding
artifact set is a trigger. That path reads this current owner and
`plan-tree.md` before generation, records both actual owner-byte hashes in the
artifact receipt, and runs the production actual-byte gate below before any
artifact handback or affected implementation. This does not widen ordinary
Init/update, unchanged-route L3/L4, routine verification, or local development
into a Project Intelligence trigger.

On a non-trigger path, do not read this body, inspect a standing Project
Intelligence carrier, scan intake/future/history surfaces, emit its block,
write owner state, call a helper/model/agent, or ask an owner-specific question.
Full and Adaptive use this same zero-load boundary.

## Scoped Authority And Orthogonal Understanding State

Keep the decision domain (`scoped_authority`) separate from the four machine
dimensions used to present one decision-relevant understanding entity. Never
collapse these dimensions into one `status` or localized label:

```yaml
provenance: user_input | primary_ai_derivation | joint_discussion | code_evidence | runtime_evidence
authority: candidate | jointly_confirmed | primary_ai_professional | conflict | superseded
freshness: current | review_required | invalid | historical
time_range: current_stage | next_stage | long_term_goal | open_idea
```

`scoped_authority` remains one of `value_authority | fact_authority |
professional_authority | risk_authority`. `provenance` records where the
understanding came from, not who may decide it. `authority` records its current
consensus/professional standing, not whether evidence is fresh. `freshness`
records the effect of current evidence, and `time_range` prevents a valid
long-term pressure from becoming a current-stage commitment.

User-facing combinations are derived views only. For example, render
`用户提出 · 待推演`, `AI 推导 · 待对齐`, `共同确认 · 当前`,
`历史用户确认 · 待复核`, `AI 专业决定 · 当前`, `存在分歧 · 需对齐`, or
`已替代 · 历史` from the four dimensions and resolved governance language.
The label must never replace machine state, promote a candidate, or establish
implementation completion. A previously confirmed item with new but
non-invalidating evidence can therefore remain `jointly_confirmed` while its
freshness becomes `review_required`; this is distinguishable from the same
authority with `freshness: current`.

User confirmation protects only the exact user-owned value/L0-L2 decision it
binds. It cannot make a factual claim true or a technical option superior.
The Primary owns domain concepts, architecture, implementation, tools, tests,
and reversible professional choices inside protected outcomes and risk bounds.
Long-term goals and future pressure may test a current architecture; they do
not automatically become current-MVP scope, Plan Tree work, user-confirmation
questions, implementation permission, or completion facts.

## Decompose Compound User Input Before Derivation

Treat a natural user statement as a compound input. Independently extract and
judge any `experience_evidence`, `value_preference`, `causal_hypothesis`,
`solution_candidate`, and `explicit_authorization`. One sentence can contain
all five; none inherits the authority of another. Preserve the user's direct
experience and value signal, test causal claims against evidence, compare the
proposed solution with independently derived alternatives, and accept
authorization only for the exact action/risk/scope it names.

The Primary must then derive the affected domain model, invariants,
counterexamples, evolution pressures, minimum direct evidence, and the small
set of truly user-owned questions from current facts. Historical methods and
past user judgments are evaluation lenses, not execution scripts. Optimize in
this order: protected meaning and goal correctness; complete reliable user
outcomes and direct evidence; recoverability and evolvability; then Token,
latency, and process cost. Efficiency work may remove scaffolding but may not
reduce required capability or quality gates.

## Own Unknowns Before Asking Questions

Classify every important unknown by the authority or evidence that can resolve
it, not by how large its implementation appears:

- `user_value_unknown`: a real product-value, user-experience, protected L0-L2,
  or user-exclusive fact choice. Give the Primary's recommendation and ask only
  for the exact value decision.
- `professional_design_unknown`: architecture, schema, interface, algorithm,
  migration representation, or other reversible professional choice inside
  confirmed outcomes and risk bounds. The Primary investigates, decides,
  records, and verifies it.
- `evidence_unknown`: a fact that code, data, tests, runtime observation, or
  another authoritative source can resolve. The Primary gathers evidence; it
  must not ask the user to substitute for missing inspection.
- `risk_authority_unknown`: an uncertainty governed by an existing destructive,
  irreversible, external-effect, release, privacy, security, or other risk
  boundary. Route it to that existing owner.

Schema, architecture, multi-file scope, code volume, future possibility, or an
`unknown` label alone does not create a user gate. When a professional choice
may cause a meaningful user-visible difference, split the questions: translate
the concrete experience or product consequence, recommend an answer, and ask
the user only about that consequence. The Primary still selects the technical
representation. For example, whether left and right wings may someday be
damaged, traded, or removed independently can be a value question; whether they
use one record with two endpoints or two records in an atomic group remains a
professional design question.

## Project Thesis And Evaluation Lenses

Before asking the user a product question, independently form a candidate
`project_thesis` that states at least:

- why the project is worth doing;
- target users and actual usage mode;
- the promised experience and what good means;
- anti-goals and current stage constraints;
- the Primary's professional challenges to weak assumptions or internal
  tensions;
- explicit unknowns, separating evidence-discoverable facts from information
  only this user can supply.

Do not make the user design the project from a blank page. Investigate available
evidence, propose the strongest current thesis and recommendation, then ask
only questions whose answers materially change user-owned value/L0-L2 meaning
or require genuinely user-exclusive information.

Use `evaluation_lenses` as scoped, falsifiable quality criteria, not a user
profile or execution script. Each lens records its project/candidate-cross-
project scope, `user_confirmed | primary_ai_derived | observed_feedback`
authority, `candidate | current | revised | retired` status, source refs, and a
counterexample boundary. One project response starts local; it must not become
a cross-project preference without repeated evidence or explicit confirmation.
Contrary evidence narrows, revises, or retires the lens. Route a lens to
Semantic Alignment only when changing the criterion itself changes important
project value or protected product meaning.

## Idea Establishment And Intake Lifecycle

For `establish_from_idea`:

1. Read all user-designated idea/requirements artifacts before questioning.
2. Treat unabsorbed artifacts as `temporary` evidence. Do not make their prose
   active protected truth merely because the user supplied a file.
3. Build the candidate thesis and the minimum four-plane model. Extract
   candidate L0 goal/final form, L1 capability/main chain, important L2
   charters, stack/cost tradeoffs, non-goals, risk/release posture, and acceptance
   expectations without treating them as already confirmed. An intake rule
   list remains candidate evidence and never substitutes for an L2 charter.
4. Challenge the highest-consequence assumption and present a concrete
   recommendation. Ask only remaining user-only, high-leverage questions about
   value, risk, material cost, or acceptance; prefer a bounded recommended
   option when useful, but no fixed one-question cadence is required.
5. Preserve answers as evidence in the active CoTend-governed brainstorm/PRD when
   binding, or existing PRD/brief/Decision/Knowledge/STATUS carriers otherwise.
   Do not create a parallel consensus or project-intelligence file.
6. Route the thesis/model proposal directly to
   `$cotend-semantic-alignment new_baseline`. That Skill alone teaches back,
   confirms, and persists each required current-MVP L0-L2 node; parent
   confirmation never confirms descendants.
7. Mark the original artifact `absorbed` only after the confirmed baseline is
   persisted into existing owners. Otherwise leave it `temporary` or archive
   it explicitly; never delete it silently.

Broad autonomous implementation remains blocked until direct Semantic
Alignment confirms the required protected baseline and the Project Intelligence
result has no blocking design/reality unknown. Safe future/non-MVP unknowns may
remain explicit without blocking unrelated current work. A technical unknown
is the Primary's investigation responsibility, not a user approval question.

## Four-Plane Current Project Model

Synthesize in the Primary's own words, with canonical links rather than copied
full prose:

1. **Value and product meaning** — thesis, target users/usage, promised
   experience, current and long-term value, current-MVP L0-L2/main-chain
   responsibilities, non-goals, boundaries, and applicable evaluation lenses.
2. **Design derivation and architecture implications** — current domain model,
   selected design views, invariants, assumptions, rejected alternatives,
   evolution pressures, and direct-evidence obligations.
3. **Current reality** — what code, data, integrations, verification, runtime,
   and user experience actually establish, including explicit claim limits.
4. **Candidates, unknowns, and evolution history** — AI-derived candidates,
   user-only unknowns, evidence-discoverable unknowns, conflicts, superseded
   refs, and the effect of resolving each material item.

At full scope also connect the complete current-MVP main chain, L1 capability
map, important L2 relationships, and exact active leaf to those four planes.
File lists, read receipts, hashes, self-report, or an activity-leaf summary do
not prove this synthesis or project readiness.

## Cross-Node Understanding Entities And Revisions

Store a decision-relevant thesis, concept, or invariant once in the existing
Project Intelligence/fact owner and give it a stable `entity_id`. Plan Tree
nodes keep only that ID and the relevant revision refs. The entity's
`affected_node_refs` is the bounded inverse lookup for node expansion,
successor impact, and dependency-directed propagation; it is not a graph
database or second route tree.

For a material revision, resolve five independent facts: operation policy,
actual reads, cited evidence, minimum dependency impact, and requested-route
permission. Inspection/citation does not make a node affected; no-write does
not make a product route blocked; an unrequested route is `not_requested`.
`impact_scope` names affected/blocked refs and only positively isolated
unaffected refs; unknown impact widens only to its honest boundary.

Before generation, Plan Tree freezes navigation status, complete active
path/node, nullable next leaf, reliable boundary and material-subject relation.
It freezes those facts, five scope facts, required
Unknowns and known route-authority findings in one
`cotend.understanding-generation-context.v2`. The producer may add a valid
finding but cannot delete or reclassify a required one. This input is not a
second owner. Its `project_route_reads` byte-bind project
Plan Tree, nodes and mirror/peer files. The validator checks them under the
current project root; the caller retains the pre-generation context hash.

```yaml
understanding_entities:
  - entity_id: UE-<stable semantic id; no date/version/revision token>
    semantic_key: <project-scoped stable semantic key>
    identity_status: owner_anchored | provisional
    entity_owner_ref: <existing owner anchor; null only while provisional>
    kind: thesis | concept | invariant
    content_ref: <one existing owner and anchor>
    revision_refs:
      current_ref: <verified semantic-contract ref or current Project Intelligence ref>
      candidate_successor_ref: <omit unless an unresolved successor exists>
    projection_refs:
      human_brief_ref: <plain-language view of this same revision>
      ai_working_contract_ref: <compact machine-working view of this same revision>
      evidence_appendix_refs:
        - <cold evidence/derivation appendix for this same revision>
    provenance: user_input | primary_ai_derivation | joint_discussion | code_evidence | runtime_evidence
    authority: candidate | jointly_confirmed | primary_ai_professional | conflict | superseded
    freshness: current | review_required | invalid | historical
    time_range: current_stage | next_stage | long_term_goal | open_idea
    scoped_authority: value_authority | fact_authority | professional_authority | risk_authority
    affected_node_refs:
      - <Plan Tree node ref>
    evidence_refs:
      - <exact evidence>
    supersedes_ref: <omit unless this entity revision supersedes another>
```

For protected L0-L2 meaning, the referenced semantic contract/digest and its
`supersedes` chain remain authoritative. A candidate may coexist with the last
verified current ref, but presentation, bare `继续`, implementation, a prior
confirmation, or a completed test cannot promote it. If new evidence only
requires review, keep the verified current ref and set its presentation
freshness to `review_required`. If evidence creates a material conflict, retain
the last verified ref as history/evidence, mark the affected current meaning
invalid for execution, create a candidate successor, and stop only the
affected route through Semantic Alignment and Route Rebase.

An entity referenced by two nodes is still one record. Adding or removing a
node ref changes the affected set, not the entity's protected meaning by
itself. A successor traverses declared affected-node and dependency refs; it
does not imply that every related node needs confirmation or reimplementation.
Owner-anchored identity is stable across revisions. Provisional identity is
candidate-only; date/version/revision tokens are forbidden in its ID/key.

## One Understanding, Three Progressive Read Layers

Each material understanding entity/revision remains one authoritative semantic
core. It may expose three references for different readers and moments; these
are projections of the same revision, not independently editable truths:

1. `human_brief_ref` is the default discussion view. Its actual Markdown must
   start with the adapter's fixed, readable orientation section before any
   conclusion or detail. `zh-CN` uses `## 这次在理解什么` followed, in order,
   by visible `主题`、`项目位置`、`承接的理解`、`负责与下游输出`、`本轮包含`
   and `本轮不包含` fields. `en` has the same six-field contract under
   `What This Understanding Covers`. Other languages require an explicit
   adapter; locale and repository text never infer one. The section has no
   table/code/schema, is non-empty, and its subject equals the AI subject.
   It then explains meaning, reality gap, recommendation, unknowns and only
   genuinely user-owned questions.
2. `ai_working_contract_ref` gives the stable entity/revision refs, projection
   refs, state, Unknown lifecycle, invalidation and readiness. New material
   sets use v4 and separately bind operation policy, actual read scope,
   evidence scope, product impact, requested-route permission, dynamic Plan
   Tree navigation and required authority findings to the frozen generation
   context. It is a compact index, never a second long explanation.
3. `evidence_appendix_refs` preserve direct evidence, support/claim limits,
   counterexamples, negative obligations, hashes, history, and unread limits.
   Load only the affected slice for derivation, important planning,
   implementation, verification, review, conflict, recovery, or a user request
   for the reason/evidence.

All three projection refs bind the same `entity_id` and revision ref. Authority
belongs to that entity/revision owner, not to any projection file. Only the
successful production validator result may report
`projection_binding_validated: true`; a receipt or projection must not self-
report it, call one projection `canonical_projection`, or infer that valid
binding makes the underlying understanding complete/current/confirmed.

The default human brief must not require stable IDs, YAML, source type names,
Evidence matrices, schema fields, or migration mechanics. The user may respond
to a natural-language heading or a local sentence; the Primary binds that input
back to the correct entity/ref. Do not impose a mechanical word cap: keep one
material topic at a time, lead with the conclusion, and expand details on
demand. Merely renaming the original dense report as a "human layer" is a
presentation defect. If the target user cannot understand the brief, do not
attribute that failure to the user's technical ability.

No projection, presentation state, user readability score, or local positive
review can confirm a candidate, prove completeness or factual correctness,
change freshness, establish implementation, or advance a route. Those remain
with the existing semantic, evidence, closure, and authority owners.

New material AI projections use `cotend.ai-working-contract.v4` under the
ref-only/8 KiB gate. Working refs use safe relative owner anchors; case/separator
projection self-truth fails. Unknown impacts stay inside affected closure and
blocked refs inside their impact. Long bodies and `canonical_projection` are
forbidden; v1/v2/v3 pairs are read-only. The v4 `navigation_context` exactly
matches the pre-generation Plan Tree snapshot: active node is the path tail,
boundary refs/state move together, unknown route facts stay explicit, and
subject relations cite owner basis. Each navigation/finding basis file has one
actual-byte `project_route_reads` entry with the correct owner/mirror role.

## Artifact Receipt And Actual-Byte Gate

Each material set uses `cotend.understanding-artifact-receipt.v4` to bind its
identity, projection/owner hashes, repair, sourced profile and context. The
validator receives the external context, current project root and independently
retained pre-generation context hash. It rejects
stale bytes, legacy `profile`, wrong owner/ref identity, lost required Unknowns
or findings, route/boundary/relation drift, project route-source byte drift,
scope mixing, synchronized producer drift, and human project-position text that
omits local route facts or hides them in one uncheckable technical line.
Producer agreement cannot replace that expected hash; v1/v2/v3 remain read-only.

The first failure wholly confined to a reversible generated carrier may be
repaired once and rechecked. It never repairs semantic meaning, evidence,
authorization, unknown impact, project truth or out-of-scope files.

A second failure, `repair_attempts > 1`, or any non-repairable failure sets
understanding readiness to `hold` and development permission to `no` for the
affected route. Do not report `supported`, `ready_to_read`, or
`projection_binding_validated`, do not continue affected product development,
and do not ask the user to choose a routine technical repair. Report the unmet
artifact gate and its stable errors, preserve the last valid truth, and route
only a genuinely user-owned value/risk decision to its existing owner.

Full and Adaptive use identical owner reads, semantic/scope fields, validation,
stops, readiness and permission; only profile/source and optional orchestration
scaffolding differ. Ordinary Init/update and non-material L3/L4 stay cold; do not run this validator.

## Minimum Design View And Adversarial Challenge

For a design-relevant trigger, read only affected protected meaning,
complete-goal/ideal-form context, route/architecture premises, any current
result, and minimum reality evidence needed to test assumptions. Select only
views that matter—for example identity/representation, state transitions,
ownership, persistence, composition/interfaces, invariants, data flow, layout,
or failure behavior. There is no universal chapter list, domain-model style,
state machine, database, or candidate count.

Perform one compact adversarial challenge against the most consequential
hidden assumption or convenient implementation bias. Prior authorship,
implementation success, and code volume do not lower the challenge.

Use evolution pressure only when it can reveal a current assumption or lock-in:

- `goal_implied`: required by confirmed complete goal/relationship;
- `goal_consistent`: compatible but not required;
- `speculative`: merely possible or interesting.

While that strength remains current, preserve this disposition boundary:

- `goal_implied` -> `implement_now | preserve_extension_seam |
  defer_without_constraint`;
- `goal_consistent` -> `preserve_extension_seam | defer_without_constraint`;
- `speculative` -> `defer_without_constraint | reject_unrelated`.

Reclassify from new evidence before using a stronger disposition.

Give each scenario exactly one current disposition:
`implement_now | preserve_extension_seam | defer_without_constraint |
reject_unrelated`. A scenario is a probe, not a future-feature task. Only a
reusable general conclusion may enter the affected existing owner under
`professional_authority`.

For every decision-relevant observable predicate, bind the decidable meaning,
coordinate/conditions/user viewpoint, tolerance or positive/negative examples,
`minimum_direct_evidence`, and `proxy_limit`. Do not test every adjective.
Structure presence, compilation, import, binding, or the Primary's explanation
proves only that exact internal fact unless the claim is limited to it.
Acceptance executes these obligations; Project Intelligence does not pretend
that defining evidence proves the result.

## Freshness And Selective Refresh

Bind the result to exact relevant value/semantic refs, route/design refs, the
minimum necessary reality evidence, and a change boundary. When a basis changes,
mark only affected views `refresh_required`, follow declared dependencies, and
mark the dependent unified execution-closure result
`revalidation_required`. Reuse unaffected conclusions and evidenced isolated
paths. A timestamp or matching hash alone cannot prove semantic or reality
freshness.

If every basis and affected boundary is unchanged, reuse the current result
without repeating synthesis, pressure generation, adversarial challenge,
persistence, or user questions. Semantic Alignment may invalidate affected
refs after a confirmed write but must not derive the replacement. Route/design
change or contrary reality may trigger refresh directly under Primary authority
when no protected semantic delta exists.

## Readiness, Stops, And Consumers

`route_permission.decision: allowed` requires a requested route in affected or
proven-unaffected scope,
`freshness.status: current`, the views needed by the selected scope, current
applicable design, no fact/route conflict, an explicit active-leaf-to-main-chain
connection when route responsibility is assumed, no blocking Unknown on that
route, `protected_semantic_delta: none`, and a collaboration state other than
`stop_affected_and_align`. A full-scope result requires all four planes plus the
thesis. A missing required domain, superseded driving assumption, stale/blocked
dependent result or pointer-only record holds only the affected/requested
route. `operation_context.project_write_policy: none` does not change that
product route state.

Only a `user_value_unknown`, value/protected L0-L2 delta, or genuinely user-only
blocking information uses `stop_affected_and_align`. Route the exact proposal,
evidence, concrete consequence, impact, and recommendation to Semantic
Alignment; Project Intelligence never confirms it. A
`professional_design_unknown` remains Primary-owned inside the existing
outcome/risk boundary, including when it affects schema or architecture. An
`evidence_unknown` triggers investigation, not a user question. A
`risk_authority_unknown` stops only through its existing risk owner. Unrelated
routes may continue.

Consumers use one result by reference:

- Plan Tree carries navigation and a compact result/ref, not this algorithm.
- Plan Tree may expose a material node's current/candidate/entity refs and
  understanding-plan-result view, but it never copies entity content or
  changes revision authority.
- Session Handoff and DMU require a current `full_current_project` result before
  takeover readiness, then add only their session/identity/code challenge.
- Semantic Alignment consumes thesis/model proposals and owns only protected
  confirmation/write.
- Closure, Acceptance, Solution Adequacy, Review, and Diagnose consume current
  invariants, assumptions, evidence obligations, freshness, and claim limits
  only on their own triggers.
- Project Init detects and propagates a real trigger only. Ordinary init/update
  remains cold and v1.91 is `future_trigger_only` with no material migration.

Full and Adaptive must produce identical thesis, planes, scoped authority,
human-brief meaning, unknown ownership, questions/stops, design, evidence
obligations, freshness, collaboration state, understanding revisions/affected
nodes, and final permission from identical evidence. Adaptive may omit ordinary
L3/L4 intermediate scaffolding, but any quality trigger uses the same necessary
analysis and verification without changing the persisted runtime profile. Only
orchestration scaffolding may differ.
